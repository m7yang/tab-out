# Context

## Domain Language

- **Dashboard**: The Tab Out new-tab surface that shows open tabs and related sources grouped for cleanup.
- **Source**: The selected dashboard input: open tabs, bookmarks, or history.
- **Dashboard Item**: A tab-shaped page from any Source that can be grouped and rendered on the Dashboard.
- **Dashboard Item Identity**: The effective page target used to decide when Dashboard Items from different Sources represent the same page.
- **Saved Page**: A user-kept Dashboard Item that stays visible in the Tabs source after its matching open tab is closed.
- **Retained Page**: A temporary, automatically captured snapshot of a genuinely closed page that may remain visible in the Tabs source for recovery.
- **Retained Page Identity**: A surface-qualified pair of normal tab or standalone app plus the existing canonical dedupe key of the effective URL; it owns one latest retained snapshot while preserving that snapshot's exact URL.
- **Retained Page Ledger**: The background-owned, device-local authority for visible Retained Pages and invisible replay-prevention boundaries.
- **Open Surface Inventory**: The session and durable records of eligible physical tab and app lifetimes used to identify genuine closures without depending on a Dashboard page.
- **Removal Boundary**: Minimal, invisible replay protection for an activated or explicitly removed Retained Page snapshot; it carries no visible page metadata and consumes no Retained Page capacity.
- **Domain Card**: A dashboard group for one registrable domain or fixed system group.
- **Domain Card Identity**: The stable `domain-*` key shared by card order memory, Domain Card view data, React keys, and card move animation DOM hooks.
- **Page Chip**: A clickable row or icon inside a Domain Card that represents one page, duplicate set, app, or folded cross-subdomain page.
- **Chip Trim**: The per-kind surface paint and seam participation of a Page Chip — active frames, group and closed-page interaction outlines, interaction fills, slot seam overlap, and interaction z-order — decided by one decision table.
- **Website Path Section**: A visible group inside a Domain Card keyed by the shortest meaningful website path prefix on a known host.
- **Path Group**: A visible group inside a Website Path Section or subdomain section keyed by a site-specific object such as a repository, project key, space key, or environment.
- **Title Suppression Scope**: The smallest visible group that owns suppressed title tokens and their matching chip markers.
- **Title Expansion**: The truncated-title treatment shared by Page Chips, Activation History rows, and Working Set rows: a clamped title fades out at the end of its last visible line, and hover-expandable titles reveal their full text in place.
- **Filter Query**: The user's parsed filter intent for app-owned matching across open-tab, bookmark, and returned history Dashboard Items.
- **Filter Match**: A decision that a Dashboard Item satisfies the current Filter Query.
- **Companion Results**: Bookmark and history results shown alongside open-tab Filter Matches.
- **Activation History**: The chronological open-tab focus path plus the bounded queue of background link tabs that have not yet been activated, used for previous/next tab switching and close-recovery behavior.
- **Pending History Tab**: An inactive tab Chrome created with an opener that has not yet been activated; it remains a distinct, indexed next target even when another pending tab has the same page URL.
- **Working Set**: A ranking signal over open-tab Dashboard Items that the user is likely to return to before scanning Domain Cards or using a Filter Query.
- **Warm Snapshot**: The newest compact in-session continuity seed: generation metadata, card order, URL-keyed Working Set priority and epoch, and session-only title-retention data. It never supplies visible first-paint content by itself.
- **Durable Checkpoint**: The restart-surviving continuity seed containing card order and URL-keyed Working Set priority; it may intentionally trail the Warm Snapshot within a target checkpoint window and never supplies visible content by itself.
- **Startup Generation**: One coherent capture of every input that determines the Dashboard's first dynamic-content state.
- **Startup Frame**: A complete Startup Generation accepted as truthful for the first dynamic-content paint.
- **Dashboard Intake**: The Dashboard page's single owner of arriving state — Startup Frame application, live refreshes, source-switch snapshots, and closed-tab updates all apply through its one store, and the page renders its snapshot.
- **Tab Action**: A user intent from the dashboard that mutates tabs or history, records undo/toast feedback, and refreshes the Dashboard.
- **Suspend Target**: The remembered third-party suspender (extension id plus an observed suspended-page URL template) used to rebuild suspend URLs when a Tab Action suspends tabs.
- **Browser Tabs Gateway**: The Dashboard's single crossing point to live browser tabs, windows, tab groups, and recently-closed sessions; it speaks browser vocabulary and absorbs browser quirks, while matching and action policy stay with Tab Actions.
- **Native Placement Bridge**: The optional, user-local native-messaging channel that accepts one versioned Hammerspoon request containing a destination kind and target display bounds, then creates a Chrome window without activating Chrome.
- **Target Focus**: Keyboard input is directed to the Tab Out Chrome window on the pointer display.
- **Target Profile Continuity**: The destination window belongs to the configured profile in the existing Chrome application; another browser application or isolated Chrome profile does not satisfy the shortcut.
- **Remote Raise**: An existing Chrome window becomes visually frontmost on a non-target display.
- **Remote Focus**: Keyboard input is directed to a Chrome window on a non-target display.
- **Remote Display Preservation**: Every non-target display keeps its active Space and frontmost window unchanged throughout and after a Tab Out shortcut, whether the destination window is reused or newly created. For a newly created destination, the guarantee also covers later whole-window closure while the remembered invocation-time non-Chrome window remains eligible. Remote Raise or Remote Focus violates this guarantee.
- **Safe Abort**: When Target Focus and Remote Display Preservation cannot both be guaranteed for the current desktop state, the shortcut makes no window or Space changes and presents a short explanation.
- **Private Exact-Window Activation**: The one-shot native operation that names a validated Chrome CGWindow ID in the WindowServer foreground/key sequence and raises that same Accessibility window.
- **Target Transition Shield**: A non-focusable snapshot canvas covering only the pointer display from immediately before bridge creation until the new exact Chrome window is active and its destination control is focused; it prevents the new inactive window from exposing its intermediate order on the target display.

## Relationships

- A **Website Path Section** uses known-host URL path rules first, then falls back to a generic first-segment section only when that segment has multiple pages in the current root/subdomain section and grouping reduces clutter.
- Tenant-style **Domain Cards** keep subdomain sections outside **Website Path Sections**, so unrelated tenants are not mixed before their website paths are grouped.
- A **Website Path Section** is visible only when it reduces ambiguity: multiple website path sections are present, or one section groups multiple pages while sibling pages remain outside it.
- **Website Path Sections** do not introduce a new indentation level unless their title-suppression summaries can stay visually aligned with the group that owns them.
- A **Website Path Section** may contain one or more **Path Groups**, and a **Path Group** may contain one or more **Page Chips**.
- **Path Group** singleton behavior belongs to the Path Group rule itself; adding a **Website Path Section** does not change whether a single site-specific object stays grouped.
- Contentful environment **Path Groups** remain visible with a single **Page Chip**, so each environment keeps an explicit scope as tabs open and close.
- A **Page Chip** shows a URL path suffix only when another chip in the same rendered group has the same visible title; sibling Website Path Sections and Path Groups already provide enough context.
- Cross-subdomain **Page Chips** fold only when both their URL path and visible title match; same-path items with different visible titles stay in their normal subdomain sections.
- Same-title **Page Chips** with different effective URLs inside the same rendered group merge visually into one title row with per-URL distinguishers; the distinguishers remain the focus, close/delete, and page-pin targets, and the merged row's favicon close action closes or deletes every closable variant at once.
- Clicking anywhere on a same-title **Page Chip** group outside a distinguisher or another self-owned action affordance activates a default distinguisher: active in the current window first, then active in another window, then the first visible variant.
- A **Page Chip** kind that draws no **Chip Trim** at rest never gains resting chrome — no frame, ring, or border appears outside interaction. Interaction feedback (hover, **Title Expansion**, context menu, tooltip) pairs the fill with a 1px outline on every full-width kind: the 22% neutral line for group and closed-page kinds (their fill barely darkens, so the line carries the signal), and the quiet fill-ink rim for open clickable chips — the same 10% mix as their interaction fill laid once more at the edge, because the darkened fill already carries the open-hover emphasis. Icon-only chips stay fill-only — their always-on ring sits outside the chip edge and would jump inward under the inset interaction line.
- Prose titles in **Page Chips** and **Activation History** use leading fixation emphasis on eligible Latin-alphabet words, including one-grapheme words, by emphasizing the first grapheme of one- to three-grapheme words and the first half of longer words rounded up. Pure numbers stay plain. Internal straight or curly apostrophes stay with their word, hyphens and dashes separate independently emphasized components, and non-Latin scripts stay plain. URL-like titles, including bare Unicode hostnames, and Jira ticket references remain plain. Filter highlights preserve complete graphemes and overlay the complete title's fixation ranges without restarting fixation at match boundaries.
- Adjacent full-width **Page Chips** overlap by one pixel so coinciding **Chip Trim** lines render as a single line; anything painting on the shared row either draws its own line there or lets the neighbour's line show through — fills are translucent or spare the shared row.
- A **Page Chip** pin is Tabs-source ordering state for an exact page identity inside one rendered sibling scope; pinned chips sort before Working Set priority but do not move across Domain Cards, subdomain sections, Website Path Sections, Path Groups, or Sources. Standalone pinned chips show a favicon-corner pin marker. Same-title URL distinguishers remain in one visual group regardless of pin state: pinned variants sort first and show a pin marker in the existing left action gutter, while the group enters the local pinned order at its earliest pinned variant.
- For `docs.google.com`, **Website Path Sections** start with document-creation product paths: `/document`, `/spreadsheets`, `/presentation`, `/forms`, and `/drawings`.
- For `*.atlassian.net`, **Website Path Sections** start with workflow/product path prefixes: `/browse`, `/issues`, `/wiki`, `/jira`, and `/servicedesk`.
- For other sites, **Website Path Sections** may use the first path segment such as `/resource`, but singleton generic segments stay flat.
- A **Filter Query** is the app-owned matching contract for open-tab, bookmark, and returned history **Dashboard Items**.
- A **Dashboard Item's** first-pass searchable text is its title and URL.
- Unquoted multi-word **Filter Queries** use tokenized AND semantics, so each term must appear somewhere in the Dashboard Item's searchable text.
- Quoted terms inside a **Filter Query** are exact contiguous phrase matches against a Dashboard Item's searchable text.
- Spaces and hyphens are equivalent separators inside a contiguous **Filter Query** term or phrase, so `tab out` and `tab-out` can match the same text.
- Unquoted **Filter Query** tokens may have app-owned aliases; `pr` matches `pull request` in first-pass matching.
- An unmatched quote in a **Filter Query** treats the rest of the input as a quoted phrase.
- Deterministic **Filter Matches** from tokens and quoted phrases are eligible for existing filtered Tab Actions.
- First-pass **Filter Matches** preserve existing Dashboard Item order rather than ranking by match quality.
- Filter highlighting marks each parsed term or quoted phrase that contributes to an app-owned **Filter Match**.
- A non-empty **Filter Query** keeps keyboard selection in the filter input by default, without virtually selecting or outlining a **Filter Match**. Arrow Down establishes virtual selection at the first currently visible match and Arrow Up establishes it at the last while DOM focus stays in the input; those arrows then move that selection without wrapping through exact Page Chip activation targets in stable Tabs, history, then bookmark order. Before a match is selected, Arrow Left and Arrow Right retain their native text-input behavior; afterward they move without wrapping according to the candidates' actual rendered positions, preferring a result in the same vertical band. **Activation History**, **Other tabs**, and collapsed overflow items are outside this result sequence.
- Local open-tab **Filter Matches** update without a fixed typing delay. The bookmark tree starts hydrating on the first non-empty **Filter Query**, and bookmark matching is local as soon as that one browser read settles. History candidate reads remain briefly coalesced while typing so filtering does not repeatedly traverse the larger browser-owned history index.
- Once established, keyboard selection follows the same **Dashboard Item Identity** when companion hydration or source-priority dedupe replaces its rendered candidate. Enter activates the selected target, or the first currently visible match while selection remains in the input; Shift+Enter and primary-modifier Enter gestures reuse the Page Chip window-move behavior. A handled result-navigation or activation key uses the current Filter Query; when only a Companion Result can satisfy it, the action remains pending until that search settles.
- **Companion Results** are loaded only while open tabs are the selected **Source**, so they do not replace the selected source view.
- **Companion Results** use Source priority while filtering: Tabs-source **Filter Matches** come first, then history **Companion Results**, then bookmark **Companion Results**. A lower-priority Companion Result does not repeat a higher-priority **Dashboard Item Identity**, but its candidate stays available so it can surface immediately when the higher-priority item disappears.
- An enabled History companion search owns a persistent unframed **History Search Summary** in the History divider with no Dashboard Item identity. Its bold status sits above the divider rule and its supporting text sits below; it stays outside the masonry grid, so real History Companion Result cards begin in the first column. It reports search freshness and the split between Chrome's returned History Filter Matches, visible History Companion Results, and matches already represented by Tabs; it never presents the returned subset as a complete history total or enters Filter Query keyboard navigation. A failed same-query refresh keeps prior History Companion Results available when they exist, while the summary reports the error and offers Retry. History Off retains the History range control but removes the summary.
- Bookmark **Filter Matches** and history **Companion Results** remain read-only **Dashboard Items** even though they render as Page Chips.
- A **Saved Page** belongs to the Tabs source, not the Bookmarks source, and saving one does not create a Chrome bookmark.
- A **Saved Page** is created only by explicit user action. Automatic closure capture creates or refreshes a separate **Retained Page** and never converts it into saved intent.
- **Saved Pages** and **Retained Pages** are eligible for normal web pages, file pages, browser settings and other internal Chrome pages, pages owned by other extensions, and standalone apps. Tab Out itself, blank/new-tab surfaces, and ephemeral non-page targets such as `javascript:`, `data:`, and `blob:` are ineligible.
- Every genuine physical closure contributes a retention candidate regardless of whether Chrome, Tab Out, a whole-window close, browser shutdown, or a future automatic action caused it and regardless of whether a Dashboard is open. Navigation, URL or prerender replacement, renderer discard, suspension, and movement between windows are not closures. Each eligible physical duplicate contributes a candidate even while another copy remains open, and a suspended surface contributes its unwrapped page target and metadata.
- Unsaved Retained Pages last for 30 days and occupy at most 500 unique identities globally, with no per-domain quota. Prune expired pages first, then the least-recently-closed identities until the cap is met. Only a newer genuine closure refreshes the snapshot or lifetime; activation, viewing, filtering, focusing, saving, or removing saved state does not.
- A **Saved Page** preserves one exact effective URL and its normal-tab or standalone-app surface kind. Saving the same exact URL once from each surface creates two independent Saved Pages; saving a same-title URL variant or folded target saves that exact target, not the visual group.
- A **Saved Page** does not follow later navigation of a matching open tab; navigation away leaves the saved exact page as a closed **Saved Page** unless the new page is saved separately. A matching open tab may refresh title or favicon metadata without changing the saved target.
- Closing a matching open tab does not remove its **Saved Page**; removing saved state does not close a matching open tab. Removing a Saved Page removes only that exact explicit record and retains its existing Undo behavior.
- A **Retained Page Identity** reuses `canonicalDedupeKey` after unwrapping a suspended URL. Canonicalization is exact by default and applies only the existing known-safe normalizations; query, fragment, path, and host differences remain distinct unless that canonicalizer already joins them.
- Each **Retained Page Identity** owns only its newest exact effective URL, latest useful title and favicon, genuine closure time, and stable closure token. Repeated physical closures refresh that one snapshot only when newer; they add no occurrence list, capacity slot, Page Chip, or duplicate count. Existing duplicate counts continue to describe physical open tabs only.
- Canonical retained identity and visual grouping are separate. Same-title and folded Page Chips may present several exact Saved Page or Retained Page targets, but each canonical identity keeps its own activation target, lifetime, capacity slot, and exact-target action.
- A matching live page suppresses a separate Retained Page chip. A matching **Saved Page** also suppresses retained presentation and its exact target, metadata, surface behavior, and save/remove action take priority. Hidden retained state keeps its independent lifetime and can reappear only after the final matching Saved Page is removed and only while still active.
- Multiple exact **Saved Pages** may share one canonical Retained Page identity. Every saved target remains independently visible and actionable; canonical projection must never discard explicit intent. When every grouped target is closed, the general Page Chip activation keeps the existing default of the first displayed Saved Page, and hidden retained state neither overrides nor reorders it.
- Saving a visible Retained Page copies its newest exact effective URL, current useful title and favicon, and surface kind into the Saved Pages store without consuming, removing, or refreshing automatic retention. Saved Pages do not expire and do not consume the 500-Retained-Page capacity.
- Choosing **Save page** from **Activation History** creates only a Saved Page, and its paired **Remove saved page** removes only that exact Saved Page; neither creates or refreshes retention. The row uses the app surface only when its canonical effective URL matches retained state unambiguously carrying the app surface; no retained match or competing normal-tab and app matches use the normal-tab surface.
- A closed **Saved Page** or visible **Retained Page** stays in its normal **Domain Card**, may match a **Filter Query**, and does not count as an open tab, live close target, or duplicate extra. Cards with only closed pages stay visible but have no live close or dedupe actions.
- Saved-only, retained-only, and combined saved-plus-retained state use the same closed Page Chip placement, shape, dimmed favicon, interaction styling, filtering, ordering, overflow, and progressive mounting. Retention adds no region, badge, icon, duplicate count, or other resting visual distinction.
- A folded Page Chip with more than 80 exact targets initially mounts 24 target pills and appends 24 more whenever its sentinel approaches the Dashboard scroll viewport. Its complete ordered target list remains in the Page Chip model, and additional mounting must not change target identity, default activation, exact-target actions, filtering, or the mounted depth of an unchanged chip.
- Domain Card copy counts actionable closed targets with generic language such as `n closed`, mixed `n + n closed`, and filtered `n/n closed`; accessible names spell out open-tab and closed-page totals. Hidden retained records and capacity slots do not add to the displayed count.
- A visible retained-only exact target offers **Save page** and **Remove from Tabs** in the existing Page Chip menu. Visible Saved state offers **Remove saved page** instead. A grouped Page Chip has no retained remove-all action, and v1 adds no global, Domain Card, filtered, or source-wide retention clear control.
- **Remove from Tabs** conditionally deletes only the acted-on Retained Page snapshot. It has no Undo and no effect on live tabs, Saved Pages, Activation History, Chrome history or Recently Closed, or physical-tab Undo; a later genuine closure may retain the page again.
- When activation consumption or **Remove from Tabs** makes the focused exact target disappear, focus moves to the next visible Page Chip target, then the previous visible target, then the **Filter Query** if its Domain Card disappears. A foreground activation keeps that pending handoff until Tab Out becomes visible again.
- A **Working Set** is merged into **Activation History**: overlapping items mark their history rows, and high-ranked items missing from history appear as supplemental history-panel rows.
- **Pending History Tabs** follow activated forward history in FIFO creation order, carry positive relative indexes using the existing history-row treatment, and become normal activated-history entries when focused. The forward-history command reaches them only after the activated forward path is exhausted. Closing a Pending History Tab removes it from the queue; active tab creation and inactive creation without a Chrome-supplied opener do not enter it.
- The rendered **Activation History** column is bounded by the tab-history max size after merging activated history, **Pending History Tabs**, **Working Set**, and recently closed rows. Activated history reserves the budget first, Pending History Tabs fill its remaining indexed capacity, and supplemental rows fill any remaining slots.
- A **Working Set** is not a **Source** and does not include bookmark or history **Dashboard Items**.
- A **Working Set** crosses **Domain Card** boundaries because it is optimized for return switching rather than domain cleanup.
- A **Working Set** prefers currently relevant open tabs: recent activations, repeated same-day navigation/use, and repeated current-week navigation/use can all raise an item, while older or monthly habits are only weak tie-breakers.
- A **Working Set** may use historical activity signals to rank items, but every visible item must focus an existing open tab.
- A **Working Set** treats active tab activation and active meaningful navigation as strong activity signals.
- A **Working Set** treats repeated same-day exact page/path use as a medium activity signal, repeated current-week exact page/path use and same-domain habit as weak activity signals, and passive open duration or background tab churn as non-signals.
- A **Working Set** ranks items by recency-dominant frecency and exposes a bounded top set as history hints, supplemental rows, and open-tab priority inside existing Domain Card scopes.
- A **Working Set** excludes Tab Out pages, folds duplicate effective URLs, and does not treat Domain Card pins as a primary ranking signal.
- A **Working Set** does not render as a standalone strip before **Domain Cards**; the fallback flow is **Activation History**, stable **Domain Cards**, then **Filter Query**.
- A **Working Set** is for switching: its supplemental **Activation History** rows support focus, URL preview, and closing the underlying open tab (with undo); broader cleanup such as dedupe and bulk close remains in owning **Domain Cards**.
- **Working Set** activity is local, bounded, and open-tab oriented; it identifies candidates by effective page identity for ranking and by live tab identity only for focusing.
- **Working Set** activity scores should mostly come from recent days, with older activity pruned or retained only as a weak tie-breaker.
- **Working Set** page identity should distinguish meaningful path changes while avoiding noisy query, hash, redirect, or background-update churn.
- **Activation History** and **Working Set** may use overlapping activity evidence, but **Activation History** is chronological switching state while **Working Set** is ranked shortcut discovery.
- **Activation History** FLIPs stable surviving rows whenever an already-painted row arrangement changes while `document.visibilityState` is `visible`; window focus and input provenance do not gate motion, so passive, keyboard, modifier, and cached-to-live updates animate when the panel may be seen. Hidden commits retain the same mounted panel's last-visible geometry and FLIP once when it becomes visible again. True first paint, filter or source replacement, materially changed panel width, rows without prior geometry, and reduced-motion mode settle immediately; close and forget keep their existing removal motion without replaying the survivor move, and tab focus is never delayed.
- **Activation History** has no relevance-based dimming tier; dimming signals liveness only. Rows whose tab is gone (dead stack rows and recently-closed ghosts) dim both favicon and title and hover with the shared closed-page chip treatment (group fill plus 1px outline); suspended-but-open rows dim only the favicon. Standalone app rows draw the same ringed favicon as `Apps` chips and show raw window titles, matching the Apps card.
- **Activation History** recently-closed rows can be focused to reopen the tab and can be forgotten with an undoable local dismissal that hides that closure from the panel; Chrome exposes no API to delete a recently-closed entry, so forgetting is local suppression keyed by effective page identity that lapses if the same page is closed again later.
- A **Working Set** does not change **Domain Card** ordering; it may prioritize sibling subdomain sections, Website Path Sections, Path Groups, and Page Chips within a Domain Card, and any future **Filter Match** ranking use should treat Working Set activity as a tie-breaker rather than replacing match semantics.
- A **Working Set** excludes utility pages such as Tab Out pages and should drop non-open pages from the visible set while retaining recent activity only as historical ranking evidence.
- A **Tab Action** may suspend the live, not-already-suspended tabs behind a **Page Chip** or **Activation History** row by redirecting them into the **Suspend Target**; folded chips suspend every matching live tab, and without a learned Suspend Target the action only reports that no suspender was detected.
- A **Tab Action** may suspend the live, not-already-suspended tabs behind a **Title Suppression Scope** token when that token has matching ungrouped, non-preserved open tabs.
- The **Suspend Target** is learned by observing an already-suspended open tab and is remembered across sessions; suspending never picks a suspender the user has not used.
- A suspended **Dashboard Item** keeps its real page's favicon: chips, history rows, and Working Set rows resolve the icon from the unwrapped effective URL instead of keeping the suspender page's faded copy.
- A **Page Chip** or **Activation History** row temporarily replaces its favicon with a Chrome-blue loading indicator while any awake open tab it represents is loading. This applies to new tabs, reloads, navigations, suspended-page wakes, duplicate sets, same-title groups, folded environments, and supplemental **Working Set** history rows; suspended, closed Saved Page, Retained Page, bookmark, browser-history-only, and recently closed Dashboard Items never show it.
- A **Dashboard Item** favicon encodes liveness: full strength only when an awake open tab backs it; suspended and closed items dim the icon on **Page Chips** and **Activation History** rows, same-title variant rows dim their per-URL label instead, and read-only Bookmarks/History sources render full strength.
- A **Page Chip** or **Activation History** row offers Reload and Duplicate only when its menu target maps to a live Chrome tab. Ordinary chips, same-title URL distinguishers, and Activation History rows act on their exact represented tab; folded chips expose these single-tab actions on individual environment pills rather than applying them to the whole folded group.
- An **Activation History** row offers the other explicit **Page Chip** context-menu actions that apply to it: copy title, copy URL, save page, and suspend.
- A **Tab Action** reads and mutates open tabs, windows, and recently-closed sessions only through the **Browser Tabs Gateway**; matching, dedupe, suspend-eligibility, and undo policy remain **Tab Action** decisions.
- Live-tab matching resolves a **Dashboard Item Identity** to the live open tabs it names — suspender-aware, including folded same-title variants — and close, mute, and suspend all resolve through that one matching.
- A **Title Suppression Scope** is owned by exactly one visible group: a **Domain Card**, Website Path Section, subdomain section, or Path Group.
- Repeated title noise inside a visible **Website Path Section** is scoped to that section when no narrower **Path Group** owns it.
- A **Title Suppression Scope** owns its summary tokens and matching chip markers; visible scopes coordinate palette colors within a **Domain Card** so two visible suppression meanings do not use the same color.
- **Title Suppression Summary** tokens render in source-title reading order, so the summary reconstructs where suppressed text came from instead of ranking tokens by frequency.
- **Title Suppression Scope** colors are allocated by token coverage before summary position; broad, high-coverage tokens can keep stable early palette colors even when they render later in the summary.
- A single-token **Title Suppression Scope** uses the same local palette as a multi-token scope for its summary token and matching chip markers when those markers span multiple rendered child groups and the **Domain Card** has more than one visible title-suppression meaning.
- Title suppression color assignment is stable across collapsed and expanded child groups.
- Title suppression colors may be reused only after the available palette colors are exhausted within a **Domain Card**.
- Neutral single-token **Title Suppression Scopes** do not consume palette colors.
- **Title Expansion** opens at most one expanded title per surface kind at a time. A Page Chip reveals truncated title details through this in-place expanded surface rather than a tooltip popup; auxiliary controls may still use normal tooltips. A Page Chip's expanded title details and interaction chrome share the same expansion state; both remain visible until the pointer leaves its expanded bounding box unless its context menu or visible keyboard focus still owns it. Activation History closes immediately when the pointer leaves its original entry slot unless its context menu still owns it.
- An expanded **Activation History** title paints above the local scrollbar, so the moving entry itself covers only the scrollbar band it currently overlaps during normal scrolling and elastic overscroll; the rest of the scrollbar remains visible and interactive. The covered band routes input through the history scroller instead of the obscured scrollbar track.
- Working Set rows use only the clamped-fade half of **Title Expansion**; Page Chip and Activation History titles are the hover-expandable surfaces.

## Runtime and Interaction Contracts

- The Tab Out Spoon captures one pointer display and active Space for every shortcut invocation. It owns destination display and Space policy, Target Profile Continuity, native-window observation and validation, and Private Exact-Window Activation; machine-local Hammerspoon configuration supplies only lifecycle, profile, and keybinding settings.
- The **Native Placement Bridge** accepts short-lived, versioned requests for inactive window creation and configured-profile window inventory. A creation request contains filtered/new-page intent and the pointer display's full bounds. The extension resolves those bounds to exactly one enabled Chrome display, regardless of display count. When a normal source window exists on another display, it translates that window's geometry into the target work area; otherwise it uses the target display's full work area, so creation does not depend on another Chrome window. An inventory request returns only normal, non-minimized browser window IDs visible to that profile's extension. Invalid, expired, ambiguous, or unsupported requests Safe Abort before mutation.
- The **Native Placement Bridge** creates one normal window with `focused: false` and its final target-display bounds in the same call, and never calls a Chrome tab/window activation API afterward. It must not create minimized and apply bounds later: Chrome cannot combine those fields, and the deferred placement can expose source-display geometry before the update commits. The filter route starts at `focusFilter=1`; the new-page route starts as Chrome's native new-tab page. When Screen Recording permission is available, Hammerspoon installs a Target Transition Shield before bridge creation, identifies and validates the new native window, performs Private Exact-Window Activation, focuses the destination control, and removes the shield only after the window is frontmost. A capture failure skips only the shield and preserves routing availability.
- The Spoon reuses a target-Space Chrome window only after verifying that it belongs to the configured profile. It can identify an unfocused configured-profile window by correlating the profile-scoped browser window IDs with a unique, focus-independent Chrome AppleScript and Accessibility fingerprint. Ambiguous or unavailable correlations never authorize reuse. If every target-Space Chrome window remains unverified or belongs to another profile, those windows remain untouched and the Native Placement Bridge creates a configured-profile window on the same destination; creation does not require a Chrome-empty target Space.
- When Chrome is stopped and the route requires creation, the Spoon launches the configured profile in the background without a startup window, waits for the profile-scoped Native Placement Bridge handshake, and then requests the directly placed destination. A failed launch or bridge timeout Safe Aborts before visible Chrome window creation.
- On a fullscreen Space, the Spoon first reuses a verified configured-profile Chrome window in place. If no reusable window exists, it switches to a regular Desktop on that display, preferring the last observed valid regular Space and otherwise the first available regular Space, before creating the destination.
- The Native Placement Bridge addresses the pointer display by full bounds and never imposes a display-count or shortcut-position limit.
- While its native port is connected, the Native Placement Bridge keeps the host and extension worker resident for immediate shortcuts. A disconnect starts a short fast-reconnect sequence whose final delay exceeds Chrome's normal service-worker idle window, so an unavailable optional host lets an otherwise idle worker terminate instead of sustaining itself with retries. A later ordinary worker wake restarts the fast sequence; this policy creates no reconnect alarm or other durable keepalive.
- Existing-window navigation begins only after the Spoon has established the exact destination display, Space, configured profile, Chrome PID, and native window ID, privately activated that window, and verified it as Chrome's front window. Bounds alone are not a window identity.
- Private Exact-Window Activation has no fallback to ordinary Chrome activation, `window:focus()`, a synthetic click, or remote z-order restoration. Missing runtime symbols, an unavailable WindowServer connection, missing Accessibility permission, or a failed postcondition becomes a Safe Abort.
- A Native Placement Bridge window remembers the invocation-time focused non-Chrome window when it remains the frontmost normal window on its display's active Space; on the target display it must remain directly beneath the exact created window. When the exact created window is still focused, the Spoon handles its red close button and Command-Shift-W before Chrome; it handles Command-W only when Accessibility proves that the window has one tab. The Spoon focuses and verifies the remembered window before closing the created window, preventing Chrome's active-window fallback from changing the prior order on either the target or a remote display. Ineligible recovery, other windows, and multi-tab Command-W remain Chrome-owned. A monitor exists only while an eligible bridge-created window exists, stops on normal destruction, and repairs final focus after Chrome lands on any remaining Chrome window even when Chrome omits the destruction event; unhandled closure paths cannot be guaranteed flash-free.
- Changes to Private Exact-Window Activation and macOS updates require manual create and reuse runs for both shortcuts against the live Remote Display Preservation oracle; isolated tests and a successful build do not replace that acceptance.
- The `focusFilter=1` page bootstrap owns only early search-field seeding and focus. It must not focus a Chrome window, create/replace tabs, or request Chrome application activation.

This section is the canonical implementation contract for durable runtime and interaction behavior. Update it in the same patch as an intentional behavior change; use an ADR for its rationale or history.

### Dashboard startup, sources, and persistence

- The Dashboard groups open tab-like items by registrable domain; homepage-like routes stay inside their normal Domain Card. The live Tabs population includes real web tabs plus Tab Out/new-tab pages, while open Chrome internal pages and unrelated extension pages stay out of normal cards. Explicit Saved Pages and Retained Pages may still place their broader eligible closed targets in those cards.
- Tab Out is unavailable in Incognito. Reject private surfaces before URL normalization, identity hashing, logging, inventory, or persistence; Startup, Working Set, Saved Page, Retained Page, inventory, pin, and history state must never persist private-browsing data into shared extension storage.
- Every dashboard load paints the header shell — filter input, source switch, reserved header-stats space, and the reserved Activation History column — from the generated page markup, before any script runs or any storage read resolves. Header stats stay blank until data exists. The React app attaches to that markup instead of replacing it, so the shell never unmounts between first paint and interactivity.
- The app's first render must reproduce the generated markup exactly, so it renders build-time defaults and never resolved stored state. Dashboard data, header actions, Activation History, Working Set, recently closed rows, their local dismissals, and stored display preferences arrive together as one **Startup Frame**, so the shell does not shift and no partial startup state flashes.
- With `focusFilter=1`, the shell's filter input is focused before the app bundle parses. Because the app attaches to that exact element, focus, selection, and the painted focus ring survive with no handoff; text typed before the bundle runs is read from the pre-app buffer and must survive the first render.
- Large source grids progressively mount Domain Cards in bounded chunks as they approach the viewport. Tabs refreshes and card reorders retain the already-mounted depth so live changes do not collapse the grid or jump its scroll position; a source or Filter Query change starts the new result set from its first chunk. Filter keyboard navigation includes only matches that have mounted.
- First dashboard-content paint uses exactly one **Startup Frame** built from live inputs. A **Warm Snapshot** or **Durable Checkpoint** may seed ordering and reconstruction, but neither supplies visible Dashboard state by itself. Freshness is all-or-nothing across the Startup Generation rather than independently admitted per surface.
- The generated shell remains visible and interactive while the live Startup Generation is captured, including after browser restart. Do not add per-input revision tracking or a current-page delta journal merely to make cached dynamic content eligible for first paint.
- Keep the shell visually quiet throughout a live capture. Do not show a loading label, spinner, or skeleton. On failure, the reserved status slot becomes `Couldn’t load dashboard` with Retry without shifting layout. Filter and source controls remain interactive, and the eventual Startup Frame reflects their latest intent.
- If no truthful **Startup Frame** can be built, the shell remains interactive and presents a compact retryable failure. Tab Out must not substitute an empty Dashboard or visibly stale cached state for an unsuccessful live read.
- A Startup Generation succeeds only when every semantic authority it displays is known: open tabs and windows, Activation History, Working Set, Saved Pages, the Retained Page Ledger, recently closed rows, closed-row dismissals, pins, and history range. Confirmed absent or empty values are known values; an unknown authority must fail the generation rather than silently default or omit its surface. Decorative metadata that changes no content, ordering, or action, such as unavailable tab-group color, may use its deterministic fallback.
- Subscribe to material browser, storage, service, and page-input changes before starting the live capture. Each change advances one page-local attempt revision; a capture may commit only when that revision is unchanged. Coalesce invalidated captures and restart them within the original attempt budget rather than painting an intermediate frame.
- A Retained Page Ledger change during startup invalidates the whole Startup Generation. After startup it schedules a coalesced, authoritative full Tabs refresh through Dashboard Intake; never install storage-event `newValue` as a retained-only patch. Hidden Dashboards converge through the existing visibility-aware refresh path.
- One live Startup Generation has a five-second whole-attempt deadline that does not reset when an invalidated capture restarts. An error or deadline releases Dashboard Intake into the retryable shell state, invalidates that attempt, and prevents any late result from committing.
- Explicit Retry, returning the page to visible, or a material input change may start a fresh Startup Generation after failure. Coalesce those triggers through one flight; do not run a timer-driven retry or backoff loop.
- Material background refreshes advance the compact **Warm Snapshot** without synchronously rewriting the **Durable Checkpoint**. Do not persist a startup view model, full Dashboard, Activation History, Retained Pages, recently closed rows, dismissals, or display preferences in either seed. One coalesced durable promotion targets the later of now or five minutes after the previous durable save and copies only restart-safe card order and URL-keyed Working Set priority; session-only title retention stays Warm because tab IDs cannot survive restart. Later Warm Snapshot changes update what will be promoted but never postpone the pending promotion. It runs once when Chrome next delivers the scheduled extension work and never repeats while no checkpoint is pending. Device sleep or platform scheduling may delay delivery, and a browser exit before promotion may leave the preceding checkpoint as the next reconstruction seed.
- A failed durable promotion may retry storage once immediately but must not schedule a failure-only alarm. The preceding valid **Durable Checkpoint** remains available, and only a later material browser event creates another promotion opportunity.
- Install initial order memory before the live Startup Frame, preserve cached Working Set priority, and hold Tabs chip order (ignoring remembered chip-order memory) until a filter or source change lifts the freeze; do not animate first-frame card moves. This freeze is ordering-only: seed reads intersect URL-keyed Working Set priority with freshly built live rows and drop closed targets. The service worker maintains the compact Warm seed in the background, at browser startup, and after debounced material events; it does not build a second render-ready Dashboard.
- Activation History survives service-worker and extension reloads within a browser session, but resets at browser startup because tab/window IDs are session-scoped. Persist each tab ID with its effective URL, clear the former ID-only schema once, and drop ID/URL mismatches before snapshot or shortcut navigation.
- One background-owned `RetainedPages` Effect service is the sole semantic writer for capture, migration, pruning, activation consumption, and **Remove from Tabs**. Dashboard pages send versioned commands and read projections; Browser Tabs Gateway performs live browser reads and recovery actions but does not own retained truth.
- The versioned **Retained Page Ledger** and prior-session **Open Surface Inventory** live in trusted-context `chrome.storage.local`; the full current-session inventory lives separately in `chrome.storage.session`. The ledger stores a SHA-256 digest of surface kind plus canonical identity, the untruncated exact effective URL, bounded useful title and favicon metadata, latest closure time, and a stable opaque closure token. The inventories keep only the data needed to identify a lifetime and capture its page; they do not persist tab-strip position, group, pin, navigation or document history, scroll, form state, or page content.
- Persist the local Retained Page Ledger as compact allowlisted v1 JSON inside a whole-store `gzip-base64-json-v1` envelope. The compact JSON omits page identity digests and Removal Boundary closure tokens already carried by their map keys and reconstructs canonical keys from exact URLs on read. Readers remain compatible with the earlier expanded uncompressed v1 value. The separate Open Surface Inventory schema 2 marks identity fields as owner-derived; legacy schema 1 reindexes from exact URL plus surface once before being rewritten, while later cold workers trust schema 2 without hashing it again.
- Retained storage is device-local and versioned separately for schema and identity rules. A known identity migration recomputes from surface kind and the stored exact URL, keeps the newest closure when records collide, and does not collapse exact Saved Pages. Preserve unknown newer versions without overwriting them. A malformed known ledger may reset only automatic retained state and report degraded recovery; storage unavailability or an unknown newer ledger fails the truthful Startup Frame instead of presenting a false empty set.
- The **Removal Boundary** stores only identity digest, stable closure token, and the removed snapshot's expiry boundary. It retains no URL, title, favicon, or visible record, consumes no capacity, expires when that snapshot would have expired, and prevents a replayed or older lifetime from reviving it across worker restart or known identity reindex.
- First installation seeds both inventories without creating Retained Pages. Browser startup treats every prior durable lifetime as closed before seeding current tabs as new lifetimes, even when Chrome restores a matching page. A worker restart within the same browser session trusts session inventory and infers only missing lifetimes; an extension reload or update preserves surviving live tab IDs, infers missing lifetimes, and reseeds current surfaces. `tabs.onReplaced` transfers the same closure token, and every reconciliation is idempotent.
- For ordinary closure, persist the ledger result before deleting the lifetime from either inventory. A valid session entry is preferred, with only a matching valid durable entry as fallback; never guess from Dashboard state, Activation History, Chrome Sessions, or browser history. An idle close batch starts at the next microtask without a timer; closure events delivered while one asynchronous transaction is in flight accumulate into the next single transaction. Each transaction marks both inventories, applies its ordered closures through one indexed ledger mutation and write, then cleans both inventories. Expired records are pruned before capacity enforcement, and stable-token replay after partial cleanup is a no-op that does not refresh time or capacity.
- Automatic capture writes retry exactly once immediately. Persistent failure leaves the prior ledger unchanged, retains the candidate where possible, never blocks or reverses the physical close, schedules no failure-only timer, and records session-only degraded health for the next visible Dashboard. Activation consumption and **Remove from Tabs** writes never retry automatically.
- Maintain one background alarm for the earliest retained expiry and also prune on every startup, ledger read, and ledger write. Alarm or cleanup failure cannot make expired state visible: projection filters it immediately and later material work retries durable cleanup.
- `Apps` renders standalone app/PWA windows as ordinary titled chips with raw window titles and ringed favicons, never active-tab highlighting or a low-score tier. `New tabs` (`__tab-out__`) and `Apps` (`__standalone-apps__`) are utility cards: unpinned by default but explicitly pinnable. Domain Card pins are local dashboard-ordering state, separate from Chrome's native `tab.pinned`; Pin/Unpin lives in the Card menu, while only pinned cards show the header pin marker and reorder handle.

### Cards, loading, and tab actions

- Within a Domain Card, Working Set priority may rank subdomain sections, Website Path Sections, Path Groups, and Page Chips. Non-prioritized chips retain remembered order across refreshes, tolerate raw/effective URL and saved/open identity drift, and update title/loading/favicon state in place. A previously observed suspended tab that wakes with the same numeric tab ID and unwrapped effective URL retains its prior title through its entire loading state regardless of initiating surface; valid page and background startup snapshots may seed that state. Completion, URL change, closure, re-suspension, any non-loading state, ordinary reload, discarded tab, or a newly created tab releases title retention. Duplicate tabs remain independent by numeric ID.
- While a matching open tab is loading, its merged Saved Page keeps the persisted Saved Page title until loading ends.
- Duplicate handling renders one chip per effective URL with a stacked-favicon marker and preserves the exact open-copy count in labels. The exact `chrome://newtab/` URL and Tab Out's `index.html` search/hash variants share one duplicate identity while retaining their physical URLs for activation and undo; other Chrome new-tab implementation URLs remain outside that identity. New-tab utility cards may bucket preserved same-identity Tab Out copies by current, Chrome-pinned, Chrome-grouped, and ordinary status. The extension toolbar badge shows the number of duplicate tabs the global dedupe policy can currently close, hides at zero, and runs that global dedupe when clicked. User-triggered bulk close/dedupe preserves Chrome tab groups; Tab Out dedupe preserves pinned Tab Out tabs and never closes the current active Tab Out page, and opening a new tab never triggers automatic dedupe.
- GitHub repository-root URLs with and without a terminal slash share the no-slash effective URL. Nested and reserved GitHub routes remain exact by default, and query or hash differences remain distinct.
- Domain-card bulk suspend and close-suspended actions have the same ungrouped, non-preserved target scope as bulk close. Bulk suspend redirects live, not-already-suspended tabs through the detected Suspend Target; close-suspended revalidates that each targeted tab is still suspended before closing it. The close-suspended menu item remains visible but disabled when its current scope has no suspended targets. Both actions leave Chrome tab groups untouched. Folded Page Chips expose exact-tab Reload/Duplicate through their environment pills while their group menu stays bulk-oriented; title-suppression tokens can close or suspend their matching ungrouped, non-preserved tabs.
- Open plain Page Chips and open Activation History rows use the quiet fill-ink hover rim; closed targets use the group-style hover outline. Current chips/rows retain their permanent ring, framed chips strengthen their frame, and no surface gains resting chrome. This supplements the favicon liveness and loading rules above.

### Filtering and direct interaction

- Filtering keeps matching open tabs in their normal cards and moves non-matching open tabs to the secondary `Other tabs` grid so every open tab remains accounted for. Chrome history search retrieves at most 100 candidates per query, while Tab Out applies its parsed Filter Query, highlighting, and Tabs > history > bookmarks source priority to those returned candidates.
- The global **Filter Query** empty state represents the complete enabled result set, not the Tabs source alone. It remains absent while Bookmark or enabled History **Companion Results** are pending, appears only after every enabled source settles successfully with zero **Filter Matches**, and never replaces a failed History status.
- History companion results use the remembered range menu: off, last day, last week, last month, last 3 months, last 6 months, last year, or all time. All time starts at the Unix epoch. The control has a same-size labeled fallback, and an enabled non-empty Tabs filter reserves its fixed-height summary from the first search frame through settlement. Enabled-range changes retain same-query results while reporting Updating; query changes clear prior results and report query-neutral Searching; failures remain distinct from zero results and retain same-query results when available. Turning History off hides the summary but keeps the control, clears the retained snapshot, and waits for the exact re-enabled scope. Synchronizing the Filter Query to Tab Out's own URL must not restart card motion.
- Hovering or focusing a Page Chip, Activation History row, or environment pill updates the exact-target URL preview. When that target is an exact live tab in a normal Chrome window, Tab Out also adds it to that window's native highlighted-tab selection without changing the active tab, raising the window, or discarding an existing multi-selection; leaving the preview removes only the highlight Tab Out added, while native user selection changes win. Duplicate chips use the same representative tab as activation, title groups use their deterministic default variant, and context menus retain their target preview while open. Page Chip expansion stays left-anchored and clamps to the right-side viewport budget rather than growing left.
- Hover-revealed close and forget controls in Page Chip favicon slots, same-title URL distinguishers, and Activation History favicon slots have reveal regions covering their full action footprint. The reveal region and control use the same pointer cursor, so first entry stays visually stable while the action becomes interactive.
- Plain click focuses the represented live tab. Cmd/Ctrl-click moves it into the current window in the background and unsuspends when needed; Cmd/Ctrl+Shift-click moves and switches to it; Shift-click moves it to a new window, falling back to a new-window URL when no live tab exists. With no live tab, the current-window gesture opens a new tab. These modifier gestures suppress native text selection on the chip/row surface.
- Activating a visible **Retained Page** recovers at most one exact page through that same modifier contract. Revalidate immediately before mutation and focus or move an exact matching live normal tab when one exists; otherwise create the intended normal tab or window from the retained snapshot's newest exact effective URL. A retained app target keeps app identity for presentation and capacity but recovers as an ordinary browser tab, reusing an exact normal-tab fallback when present. Fresh recovery does not restore the former index, pin, group, suspension wrapper, navigation history, scroll, form state, or standalone app window.
- Retained activation is single-flight per identity across Dashboard pages and never calls `chrome.sessions.restore()`; Activation History alone owns Chrome session restoration. Only confirmed exact recovery conditionally consumes the acted-on closure token. A newer closure wins over delayed consumption, an unavailable or unconfirmed target preserves the record, and browser success followed by storage failure keeps both the recovered page and Retained Page while reporting that Tabs could not be updated. Never automatically retry consumption or reverse the browser action.
- **Remove from Tabs** uses the same exact identity-and-closure-token comparison. Concurrent removal of one snapshot is idempotent, already-absent or expired state is successful completion, and a newer closure defeats delayed removal. Rejected persistence keeps the page visible and receives no automatic retry.
- Activating a suspended page first asks its owning suspender extension to unsuspend that exact tab, then falls back to navigating the same tab to the unwrapped URL. Undo for close/dedupe restores tabs with `chrome.tabs.create({ active: false })`; do not substitute `chrome.sessions.restore()` unless deliberately changing the focus contract.

## Flagged Ambiguities

- **History Companion Results** still rely on Chrome history search semantics for candidate retrieval. Tab Out applies its app-owned **Filter Query** to returned candidates; fetching broader candidates for app-owned aliases that Chrome does not return remains deferred.
